CPP真是个很操蛋的语言，用着很烦，经常又不得不用。它生来就给自己设定了枷锁 —— 高度兼容于C，随着编程范式的出现，又不得不继续蹩着脚前进，始终记得兼容性是第一位的，所有被检验过的老范式它都支持。有时也不得不感慨它也很新，熟知的面向对象、泛型编程也早有涉及，垃圾回收也插足一脚，甚至并发编程的协程概念也逐渐出现，它在进步可总觉得没那么好用，这么一摊东西揉到一起，本身就需要魔法，很多魔法。那么，魔法重要么？

typeid操作符（operator）用于查询类型的信息（std::type_info），参数支持类型（type）和表达式（expression）形式。

  • typeid获取的是静态类型信息，因此通过多态对象的基类指针获取的类型信息不一定是准确的

  • std::type_index.name()是对std::type_info.name()的包装

类（class）

默认函数

在 C++ 中，每个类会默认生成一些特殊的成员函数，这些函数称为编译器生成的默认函数。这些函数的存在为类提供了基本的行为支持（如复制、移动、销毁等），但在某些情况下，编译器可能会阻止生成这些默认函数。

函数类型 何时生成 何时不生成（被阻止）
默认构造函数 没有定义任何构造函数时 类中有自定义构造函数或禁用默认构造函数
拷贝构造函数 没有显式定义拷贝/移动构造函数时
默认浅拷贝实现		 包含无法拷贝的成员（如 std::unique_ptr）
拷贝赋值运算符 没有显式定义拷贝/移动赋值运算符时
默认浅拷贝实现		 包含 const 或引用成员，或基类/成员禁止拷贝
移动构造函数 （C++11）类支持移动语义
没有定义拷贝/移动构造函数		 包含无法移动的成员，或基类/成员禁止移动
移动赋值运算符 （C++11）类支持移动语义
没有定义拷贝/移动赋值运算符		 同上
析构函数 始终生成 显式定义了析构函数
  • 定义了析构函数，则拷贝和移动操作不会隐式生成。
  • 包含无法拷贝或移动的成员：类中包含不可拷贝或不可移动的成员（如 std::unique_ptr），则编译器不会生成拷贝或移动函数。
  • 类中包含引用类型成员：引用类型必须在构造时初始化，无法被拷贝或重新赋值。
  • 类中包含 const 成员：常量成员必须在构造时初始化，无法通过赋值修改。
  • 继承中的特殊情况：如果基类的某些函数被 delete 或私有化，则派生类无法生成对应的默认函数。

右值引用 (T&&)

右值引用 (T&&) 是 C++11 引入的特性，主要用于优化性能和实现移动语义。

实现移动语义

  • 使用 std::move 显式转移所有权
    • 将左值转换为右值以触发移动语义。
    • 避免不必要的拷贝操作。
      • 在返回值优化不可用的情况下，通过右值引用减少拷贝。
      • 可以提高性能，尤其是在处理大对象时。
  • 避免误用右值引用
    • 使用 std::move 将左值 a 转换为右值 b 后，左值 a 不应再使用，其内容是未定义的。
  • 避免返回局部变量的右值引用
    • 局部变量在函数结束后会被销毁，返回右值引用会导致悬空引用。

优化函数性能

  • 实现高效的工厂函数
    • 使用右值引用避免不必要的拷贝操作。
    • 返回一个临时对象的右值，可以被调用者高效接收。
  • 完美转发（使用 std::forward）
    • 保留传入参数的左值或右值特性。
    • 提高函数模板的通用性。
      –实现移动容器内容
    • 高效转移容器内容，避免深拷贝。
    • 对于动态内存分配的容器（如 std::vector、std::string），移动语义显著提升性能。

优化类的性能

移动构造函数和移动赋值运算符

  • 避免不必要的资源拷贝，提高性能。
  • 转移资源所有权而不是复制资源。

优化资源管理类

  • 在管理动态资源的类中，通过右值引用实现高效的资源转移。
  • 避免多次分配和释放资源。

用于延迟初始化或惰性加载

  • 利用右值引用和 std::move 高效初始化数据，减少资源浪费。

智能指针（Smart Pointer）

智能指针是一个类模板，通过 RAII（Resource Acquisition Is Initialization）模式管理动态分配的内存。在生命周期结束时，智能指针会自动释放所管理的资源，无需手动调用 delete。

  • 避免裸指针管理：不要直接使用 std::unique_ptr 或 std::shared_ptr 的裸指针进行资源管理，可能导致双重释放问题。
  • 自定义删除器：为智能指针提供自定义的删除器，管理特殊资源。
    std::shared_ptr<FILE> file(fopen("test.txt", "r"), fclose);

std::unique_ptr

  • 独占所有权：只能有一个 unique_ptr 拥有同一资源。
  • 不可复制（可移动std::move）。
  • 适合用于函数内部或类的私有成员，避免对象共享。
  • general
  • deleter
  • raw-pointer
  • others
  • 优先使用 std::make_unique（C++14） 创建
    • 避免手动调用 new，减少内存泄漏和异常导致的资源泄漏风险。
    • std::make_unique 不支持自定义删除器，当需要自定义删除器时，直接使用 std::unique_ptr 的构造函数。
  • 转移所有权时使用 std::move
    • std::unique_ptr 不支持复制，但支持移动操作，需要显式使用 std::move 转移所有权。
      • 显式 std::move 可提高代码可读性和意图的明确性。
      • 尝试复制会导致编译错误。
  • 避免和 std::shared_ptr 混用
    • 如果资源在生命周期中需要从 std::unique_ptr 转换为 std::shared_ptr，直接通过 std::move 创建。
      • 避免多个智能指针管理同一资源。
  • 配合标准容器使用
    • 使用 std::unique_ptr 代替裸指针，避免手动释放动态分配的对象。
    • 特别适合用于 std::vector 等容器管理动态对象的场景。
  • 可用于动态数组管理
    • 自 C++14 起，std::unique_ptr 支持动态数组，但推荐使用 std::vector 管理更复杂的场景。
  • 用于类的成员变量
    • 通过 std::unique_ptr 管理动态分配的类成员变量，可以避免手动管理其生命周期。
      • 适合需要独占访问权限的场景。
  • 自定义删除器
    • 在需要特殊资源管理（如文件、套接字）的场景，可以通过自定义删除器释放资源。
  • 避免裸指针的直接使用
    • 避免使用 get 获取裸指针进行资源管理或赋值，容易导致双重释放或未定义行为。
    • 如果需要裸指针，只用于短暂访问，不要直接传递或保存。
  • 避免自定义的 delete 与裸指针混用
    • 如果资源需要特殊释放逻辑，优先通过自定义删除器传递逻辑，而不是直接用裸指针管理。
  • 常用方法
    • reset 可以释放当前资源并重新分配新资源。
    • release 释放所有权并返回裸指针。

std::auto_ptr（C++11 起废弃）

  • 已被 std::unique_ptr 替代，存在复制语义问题，会导致非直观的所有权转移。

std::shared_ptr

  • 共享所有权：多个 shared_ptr 可以同时管理同一资源。
  • 使用引用计数：当引用计数为 0 时，自动释放内存。
  • 适合用于复杂对象生命周期的管理，如异步操作或资源池。
  • 用作返回值时：
    • 如果需要保护共享对象，返回 std::shared_ptr<const T>。
    • 如果不需要特殊限制，直接返回 std::shared_ptr<T> 即可。
      • 避免返回 const std::shared_ptr：它限制了指针本身的操作，但不会限制共享对象的操作，通常是没有意义的。
  • constructer
  • deleter
  • raw-pointer
  • multithread
  • others
  • std::make_shared 会将对象和引用计数存储在一块连续的内存中，减少内存分配次数，但不支持自定义删除器。
    • 应尽量避免手动调用 new，容易引发异常导致内存泄漏。
      • 当构造函数是私有的，std::make_shared 需要为友元函数才能使用，此时建议直接调用 new。
    • 如果需要自定义删除器，避免 std::make_shared 的方法。
      • 连续内存分配和自定义删除器可能产生冲突，因为自定义删除器通常希望管理独立的内存分配。
  • 从 this 指针创建 std::shared_ptr 的要求：
    1. 确保类继承 std::enable_shared_from_this
    2. 从外部使用 std::make_shared 创建实例后，通过自定义方法调用 shared_from_this()
    • 避免在构造函数和析构函数中调用 shared_from_this()，因为引用计数器可能尚未初始化或已经销毁。
  • 自定义删除器
    • 如果需要管理非标准资源，可以自定义删除器。
  • 避免重复创建 std::shared_ptr
    • 避免从 std::shared_ptr 直接获取裸指针 (get) 再次构造新的 std::shared_ptr，否则会导致重复管理同一块内存并引发未定义行为。
  • 避免使用裸指针与 std::shared_ptr 交互
    • 应尽量避免从 std::shared_ptr 直接获取裸指针 (get) 并传递给其他代码，以免导致资源管理混乱。
    • 如果需要裸指针，只在访问资源时短暂使用。
  • 避免与原生指针混用
    • 不要用 std::shared_ptr 管理第三方库返回的资源，除非明确知道资源的释放方式。
  • 多线程环境下的使用
    • std::shared_ptr 的引用计数是线程安全的，多个线程可以安全地增加或减少引用计数。
    • 但被管理的对象本身的读写访问需要额外的同步机制（如 std::mutex）。
  • 避免循环引用
    • std::shared_ptr 可能因循环引用导致内存泄漏，此时需要使用 std::weak_ptr 断开循环。
  • 常用方法
    • reset 用于释放当前对象或重新分配新对象。
      • 如果其他 std::shared_ptr 仍在共享该对象，调用 reset 并不会立即释放内存。
    • use_count 可以查看当前引用计数，但不要依赖它的值进行逻辑判断，因为多线程场景中引用计数可能随时变化。

std::weak_ptr

std::weak_ptr 用于解决循环引用问题的智能指针，和 std::shared_ptr 搭配使用。它不拥有资源，而是观察资源，适用于需要非强引用的场景。

  • 弱引用：不增加引用计数，避免循环引用。
  • 必须转换为 shared_ptr 才能访问资源。
    • 不要尝试通过 weak_ptr 获取裸指针或直接解引用，容易导致未定义行为。
  • 与 shared_ptr 配合，避免循环引用，适合用于缓存、观察者模式等弱引用场景。
  • CircularReference
  • Observation
  • shared_from_this
  • multithread
  • 打破循环引用
    • 当两个或多个对象通过 std::shared_ptr 相互引用时，会形成循环引用，导致资源无法释放。
    • 使用 std::weak_ptr 替代其中一个 std::shared_ptr，可以打破循环，避免内存泄漏。
  • 常用方法
    • lock 返回一个有效的 shared_ptr，或 nullptr（资源已释放）。
    • expired 检查资源是否已释放。
  • 获取资源时检查有效性
    • std::weak_ptr 不增加引用计数，所观察的对象可能已经被释放。
    • 在使用资源前，需调用 lock() 获取一个临时的 std::shared_ptr 并检查其有效性。
  • 用于观察生命周期管理的对象
    • 在多线程或事件驱动的环境中，std::weak_ptr 可用于观察对象的生命周期，避免直接持有对象的所有权。
    • 避免资源释放后访问悬空指针。
  • 配合自定义数据结构使用
    • 在自定义数据结构（如缓存或观察者模式）中，std::weak_ptr 非常适合用来管理可能过期的对象。
  • 配合 std::enable_shared_from_this 使用
    • 如果一个对象需要在其成员函数中获取自身的 std::shared_ptr，可以继承 std::enable_shared_from_this。
    • 通过 std::weak_ptr 配合使用，避免循环引用。
  • 避免多线程中不当使用
    • std::weak_ptr 本身是线程安全的，但在多线程环境中获取和使用资源时，需结合适当的同步机制。

转换（casting）

  • upcasting
  • downcasting
  • reference
  • 向上转换（upcasting）：派生类指针可以隐式转换为基类指针。
    • 向上转换是安全的，因为派生类是基类的扩展，所有基类成员在派生类中都存在。
  • 向下转换（downcasting）：基类指针可以显式转换为派生类指针。
    • dynamic_cast、std::dynamic_pointer_cast：运行时安全，推荐使用。
      • 需要启用 RTTI（运行时类型识别，通常默认启用，编译时加 -fno-rtti 禁用）。
      • 如果基类没有虚函数，使用时会编译失败。
      • 转换失败时会返回 nullptr。
    • static_cast、std::static_pointer_cast：无运行时检查，需确保安全性。
      • 不检查安全性，适用于开发者明确知道转换的合法性。
      • 使用错误的类型会导致未定义行为。
    • reinterpret_cast：低级操作，直接重新解释位模式。
      • 不进行任何安全检查，使用时需要极大的谨慎。
      • 适用于低级别操作，比如位模式转换，不推荐用于普通对象的转换。
  • 引用转换：类似于指针，但无法为 nullptr。
    • 使用引用进行向下转换时，如果失败，dynamic_cast 会抛出 std::bad_cast 异常。

vector

  • 动态数组：连续的内存空间存储元素，类似于数组，但大小可以动态变化。
  • 动态增长（性能开销大，合理预估容量很重要）：当插入元素超出当前容量时，自动重新分配更大的内存空间（增长因子一般为 1.5-2 倍），并将原有元素复制到新的内存空间。
  • 随机访问：支持通过下标 [] 或 at() 方法进行快速随机访问，时间复杂度为 O(1)。
  • 尾部插入/删除效率高： 在尾部进行插入和删除操作的效率很高 O(1)，但在中间或头部插入/删除元素则效率较低 O(n)，因为需要移动其他元素。
  • 最佳实践：
    • 避免频繁的内存重新分配： 如果可以预估 vector 的大小，使用 reserve() 预分配内存，可以显著提高性能。
    • 使用 emplace_back() 代替 push_back()： 在 C++11 及以上版本中，emplace_back() 可以直接在 vector 的尾部构造元素，避免不必要的拷贝或移动操作，效率更高。
    • 注意迭代器失效： 当对 vector 进行插入或删除操作时，可能会导致迭代器失效。

  • capacity()：分配的存储空间。

deque

  • 双端队列：允许在两端（头部和尾部）进行高效的插入和删除操作。
  • 动态数组扩展：支持动态增长，不仅可以像 vector 一样在尾部扩展，还可以在头部扩展，而无需像 vector 那样移动大量元素
  • 分段连续存储：连续块结构，支持两端快速扩展，不保证所有元素在内存中连续存储，避免了 std::vector 的整体扩容代价
  • 随机访问：支持通过下标 [] 或 at() 方法进行随机访问，时间复杂度为 O(1)，虽然略逊于 vector，但仍然非常高效
  • 两端插入/删除效率高：在头部和尾部进行插入和删除操作的效率很高 (O(1))
  • 适用场景：需要在两端进行频繁操作的场景，例如消息队列、双端缓冲区。

异常（Exception）

C++ 中的异常处理提供了一种处理运行时错误的机制，但它的使用需要遵循一定的规则和最佳实践，以确保代码的健壮性和可维护性。

  • 仅在异常情况下使用异常
    • 用于处理非正常流转的错误情况，如资源分配失败、操作系统调用错误等。
    • 对于可以通过逻辑控制的错误（如简单的参数检查），不要使用异常。
  • 捕获异常时使用引用
    • 使用引用（const std::exception&）来捕获异常，避免不必要的拷贝。
    • 捕获异常时，尽量捕获基类类型（如 std::exception），以便处理所有标准异常。
  • 尽量避免捕获所有异常
    • 仅在顶层入口处使用 catch (...) 作为最后的防线。
    • 通常应捕获具体类型的异常，明确处理逻辑。
  • 在顶层入口捕获所有异常
    • 确保异常不会未捕获而导致程序崩溃。
    • 提供日志记录或错误报告机制。
  • 在适当的位置捕获异常
    • 异常应在能够有效处理的地方捕获，而不是随意传播。
    • 如果某一层无法处理异常，应将其传播到更高层处理。

异常类（std::exception）

  • 使用 std::exception 及其派生类
    • 始终继承自 std::exception，便于统一处理。
    • 自定义异常时，覆盖 what() 函数提供错误信息。
  • 异常应表示错误状态
    • 异常类的命名应该明确表明错误类型，且异常信息要尽可能提供有用的上下文。

异常安全的函数设计

  • 确保函数在异常发生时不泄漏资源或处于不一致状态。
  • 遵循异常安全性保证：
    • 基本保证：异常发生后，程序状态是可知的。
    • 强保证：异常发生后，程序状态保持未变。
    • 无异常保证：函数不抛出异常（如析构函数）。

异常安全的类设计

  • 谨慎使用构造函数抛出异常
    • 构造函数抛出异常时，C++ 会自动销毁已成功构造的成员或基类，并释放已经分配的资源。
    • 结合容器使用的风险（容器直接管理指针，可降低直接存放抛异常的对象的复杂性）：
      • 可能导致部分元素被销毁：容器可能会重新分配内存并触发拷贝/移动构造，如果在某些元素的构造或迁移过程中抛出异常，可能导致容器的状态不完整。
      • 异常安全性：容器的操作需要保证强异常安全性（如 std::vector::push_back 会在异常发生时回滚到操作前的状态），但如果用户类没有正确实现移动/拷贝语义，可能导致未定义行为或资源泄漏。
    • 推荐场景
      • 无法恢复的错误： 如果构造函数无法完成对象的创建，并且无法通过其他方式恢复，则抛出异常是合理的。
      • 依赖外部资源： 例如文件打开失败、网络连接失败等场景。
    • 最佳实践
      • 始终结合 RAII 和智能指针（如 std::unique_ptr 和 std::shared_ptr）管理资源，确保异常安全。
      • 在复杂构造逻辑或需要延迟初始化时，工厂模式或静态创建方法是更好的选择。
  • 使用 RAII 和智能指针管理资源
    • 避免在异常处理时显式释放资源。
    • 使用 RAII（Resource Acquisition Is Initialization）和智能指针（如 std::unique_ptr）确保资源在异常发生时也能自动释放。
  • 避免在析构函数中抛出异常
    • 如果析构函数抛出异常，可能导致程序终止（如在栈展开期间发生新的异常）。
    • 如果需要报告析构中的错误，使用日志或其他非异常机制。
    • 如果构造函数和析构函数都抛异常，可能导致 std::terminate 被调用。

内存（Memory）

布局

  • 虚拟内存（virtual memory）被划分为页（page，连续地址的内存块，通常为4KB）
    • 当读写未映射到物理内存上的页时（missing page interruption，缺页中断），操作系统会将页对应的内容从磁盘装载到物理内存
    • 当物理内存不足时，物理内存中的页也会写回磁盘
  • 从堆（heap）中申请的内存，如果未释放，会导致内存泄漏，即虚拟内存会不断增加。如果申请的堆内存未被使用，并不会映射到物理内存，因此物理内存此时不会增加
  • 每个线程均有独立的栈（stack）空间，其是连续的内存，大小（默认1MB）在线程创建时指定，此内存会自动被回收
    • 栈中数据：
      • 函数参数入栈
      • 函数返回值入栈
      • 函数内的本地变量入栈
    • 栈溢出（stack overflow）的可能原因：
      • 随着函数调用层级逐渐加深，栈空间消耗越来越大

对齐

Purpose of memory alignment

  • CPU在32位处理器中总是按4字节进行读取，访问未对齐的内存时，需要先找到4字节对齐位置，然后通过偏移量再找到数据位置，访问速度慢一些
  • CPU操作对齐的内存是原子性的，这意味着没有其他操作会中断它，这对并发编程中的lock-free数据结构很关键
